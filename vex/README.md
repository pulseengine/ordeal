# VEX judgements (#146 / TR-043)

`judgements.json` holds the **human** half of ordeal's CycloneDX VEX. The
machine half — which RustSec advisories match which crate — is generated by
`scripts/vex.py` from the shipped lockfile. The generator never writes a
judgement of its own: an advisory that matches the shipped closure without
an entry here is published as `in_triage`.

## When you need to edit this file

The weekly *VEX re-issue* workflow opens an issue labelled `vex-reissue`
when a new advisory matches a released ordeal's shipped closure. Resolve it
by adding one entry per advisory id:

```json
{
  "RUSTSEC-2099-0001": {
    "state": "not_affected",
    "justification": "code_not_reachable",
    "detail": "Only the `foo::bar` path is used; the vulnerable `baz` API is never called (see crates/ordeal/src/x.rs).",
    "classified-by": "your-github-handle",
    "classified-at": "2099-01-01"
  }
}
```

- `state`: a CycloneDX 1.5 analysis state — `resolved`,
  `resolved_with_pedigree`, `exploitable`, `in_triage`, `false_positive`,
  `not_affected`.
- `not_affected` requires a CycloneDX `justification` and a written
  `detail`; `false_positive` requires a `detail`. Every entry records
  `classified-by`. `scripts/vex.py` refuses anything else.
- If you also suppress the advisory in CI, add the same id to `deny.toml`
  `ignore` — the two must agree.

Then run the *VEX re-issue* workflow by hand with `publish: true`. It
publishes `ordeal-<ver>.vex.r<N>.json` with its own cosign bundle; the
release-time VEX (inside the signed `SHA256SUMS.txt`) is never modified.

## Scope, stated plainly

The VEX covers the **shipped closure**: the crates a release binary is built
from (`ordeal` + its normal dependencies at default features — today just
`ordeal-lrat`). Advisories on dev, bench, fuzz or optional-feature crates are
not statements about the product; they are listed in the
`ordeal:out-of-closure-advisories` property and gated separately in CI.
