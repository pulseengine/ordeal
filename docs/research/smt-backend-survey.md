# SMT/SAT backend survey for ordeal

*A certificate-checked QF_BV solver for loom (verified WASM optimizer) and
synth (verified WASM→ARM codegen). Grounding: loom issue #246.*

**Status:** research survey, phase P1/P2 grounding. Skeptical and concrete;
every load-bearing claim is cited. Where the `wasm32-wasip2` constraint forces a
different choice than a native project would make, it is flagged **[wasip2
forces this]**.

---

## 0. What ordeal actually needs (the ruler)

Every option below is judged against **these** needs, not against "good SMT
solver" in general:

- **Fragment:** QF_BV, widths 8/32/64. Ops: `bvadd bvsub bvmul bvudiv`,
  `bvand bvor bvxor`, `bvshl bvlshr bvashr`, `bvrotr`, `extract concat`,
  `zero_ext sign_ext`, signed+unsigned compares. One-shot `check-sat`, expecting
  **UNSAT** (equivalence: assert `optimized ≠ original`) plus a **SAT
  counterexample model**. Later: a thin non-extensional `Array(BV32→BV8)` +
  uninterpreted-function-congruence sliver (loom only; synth needs *neither*).
  No quantifiers, FP, `Optimize`, or incremental `push`/`pop`.
- **HARD #1 — builds & runs as `wasm32-wasip2`.** loom self-hosts as a wasm
  component; ordeal must run in-process there.
- **HARD #2 — certificate-checked (CompCert pattern).** Untrusted solver emits
  an LRAT/DRAT UNSAT certificate; a small formally-verified checker validates
  it. Blueprint = Lean 4 `bv_decide`.
- **HARD #3 — the verified checker must be provable via an *existing* org
  toolchain:** Aeneas→Lean (`rules_lean`), Rocq (`rules_rocq_rust`), or Verus
  (`rules_verus`). User's leaning: Aeneas→Lean, "not lots of math."
- Permissive license (Apache-2.0/MIT). Fast enough to gate CI. Thin Rust API.

**A note on the existing `ARCHITECTURE.md`.** The committed architecture doc
names **"CaDiCaL (primary), varisat (wasm32 fallback)."** This survey concludes
that framing is **inverted by HARD #1**: for the target that actually motivates
the whole project (loom-as-wasm-component), the pure-Rust core is the *primary*
path and CaDiCaL is the native *fast* path. See §1 and §5(d). This is the single
most important correction the research produces.

## 1. Round 1 — pure-Rust / wasm-buildable SAT cores with proof emission

The trust boundary makes the SAT core **untrusted** (a bug can only fail to
produce a valid certificate, never smuggle a wrong UNSAT past the checker). So
the core is chosen on *maturity × license × wasip2-buildability × proof-format*,
not on soundness.

| Core | Lang | License | Proof out | Maintained | no_std / wasm | Verdict |
|------|------|---------|-----------|------------|---------------|---------|
| **varisat** | pure Rust | **Apache-2.0/MIT** | **LRAT** (native, from own format; +trimming) | **Stale** (0.2.1, May 2019) | no explicit wasm/no_std | **Primary candidate** for wasip2 — only mature pure-Rust core with native LRAT and a permissive license |
| **splr** | pure Rust | **MPL-2.0** | **DRAT only** | **Active** (0.17.6, Feb 2025) | **`no_std` + `platform_wasm` feature (2024)** | Strong wasm story, but **DRAT-only** and **MPL-2.0** (weak-copyleft, *not* Apache/MIT) both cut against the constraints |
| **batsat** | pure Rust | Apache/MIT | none documented | low | unknown | No proof output → disqualified as cert source |
| **CreuSAT** | pure Rust | **MIT** | **none** (it's a verified *solver*, not a cert emitter) | thesis; tooling "broken" | not addressed | Interesting but wrong shape — see below |
| **RustSAT** (chrjabs) | Rust lib | **MIT** | VeriPB (via `pigeons`), **not LRAT/DRAT** | active (arXiv 2505.15221, 2025) | not documented | A *library/interface layer* over C solvers, plus a pure-Rust MiniSat port; not itself an LRAT source |
| CaDiCaL | C++ | MIT | **LRAT (native `--lrat`)** | active (2.0, CAV'24) | **[no wasip2-native build documented]** | Native fast path only — see §5(d), HARD #1 |

Load-bearing details, verified:

- **varisat has a native LRAT pipeline** (`varisat-lrat`, `varisat-checker`),
  dual **Apache-2.0/MIT**, LRAT generated by converting from its own proof
  format ("much faster" than DRAT→LRAT). Generation is **opt-in** and carries
  **"High" solving overhead** — acceptable because ordeal's queries are tiny
  (per-op equivalence). Its built-in checker is **unverified and NOT a
  standalone LRAT checker** (it checks varisat's *own* format); the manual
  itself points users at the **ACL2 formally-verified CLRAT checker** for real
  assurance. So: use varisat to *produce* LRAT, do **not** trust its checker.
  <https://github.com/jix/varisat> ·
  <https://jix.github.io/varisat/manual/0.2.1/print.html>
- **splr is the better-maintained core but loses on two constraint axes**:
  **DRAT-only** (no native LRAT — you'd need drat-trim/lrat to upgrade, adding a
  trusted-ish step) and **MPL-2.0** (file-level copyleft; the constraint asks
  Apache/MIT). Its explicit **`no_std` + `platform_wasm`** support is the best
  wasm posture of the group, so it stays a live fallback if varisat's staleness
  bites. <https://github.com/shnarazk/splr>
- **CreuSAT is a verified solver, not a certificate emitter.** MIT; proves both
  SAT and UNSAT verdicts and panic-freedom via **Creusot/Why3**. But it does
  **not** emit LRAT/DRAT, its tooling is noted "broken," and it's a thesis
  artifact. It does **not** fit ordeal's untrusted-solver + verified-checker
  split (it collapses the split by verifying the whole solver — a multi-person-
  year proof the org explicitly declined). Useful as a *reference* and a source
  of Creusot patterns, not as the engine.
  <https://github.com/sarsko/CreuSAT> ·
  <https://sarsko.github.io/_pages/SarekSkotåm_thesis.pdf>
- **No newer (2024-2026) pure-Rust CDCL core with native LRAT** surfaced beyond
  these. RustSAT (SAT Competition-adjacent, 2025) is an *interface library*
  (bindings to CaDiCaL/Kissat/Glucose/MiniSat, a pure-Rust MiniSat, VeriPB proof
  logging for *encodings*), not a drop-in LRAT-emitting solver.
  <https://github.com/chrjabs/rustsat> · <https://arxiv.org/abs/2505.15221>

**Round-1 conclusion.** For the wasip2-primary path, **varisat** is the least-bad
mature choice: pure-Rust, Apache/MIT, native LRAT. Its 2019 staleness is the
real risk and must be mitigated (vendor + pin, small maintenance fork if
needed). **splr** is the maintained fallback if we can accept DRAT+MPL. The
matrix has *no* ideal entry — a genuine gap flagged for §4.

## 2. Round 2 — QF_BV bitblasting for a wasm target

The bitblaster is **untrusted** (below the trust boundary), so it may be written
in ordinary fast Rust; nothing here forces native code.

- **Standard, well-trodden pipeline:** term-graph → per-op boolean circuit →
  **AIG** (And-Inverter Graph, structural sharing + cheap const-folding /
  strashing) → **Tseitin CNF** (one fresh var per gate, linear size) → SAT.
  Boolector, Bitwuzla, Yices2, and Lean's `bv_decide` all bitblast this way;
  Beaver (UCB) and Bitwuzla use AIG→CNF via ABC-style logic.
  <https://www2.eecs.berkeley.edu/Pubs/TechRpts/2010/EECS-2010-67.pdf> ·
  <https://bitwuzla.github.io/data/NiemetzPZ-CAV24.pdf>
- **The AIG layer is the important design choice, and it must be *ours* and pure
  Rust.** There is no mature standalone pure-Rust AIG-for-QF_BV library to reuse
  (RustSAT is CNF-level, not word-level; ABC is C). This is *fine* — ordeal's
  fragment is small and fixed, and `ARCHITECTURE.md` already commits to writing
  the bit-blasting rules op-by-op with structural sharing. **Nothing in the
  bitblasting layer must be native.** [wasip2: neutral — pure Rust builds
  cleanly.]
- **`bv_decide` is the exact blueprint and it's *verified*:** it bitblasts
  `BitVec`/`Bool` into a **verified AIG** (designed like AIGNET), then CNF, ships
  to CaDiCaL, and checks the returned LRAT inside Lean's kernel. Ordeal copies
  the *architecture* (AIG→CNF→SAT→LRAT→checked) but ordeal's bitblaster stays
  untrusted Rust; only ordeal's *checker* needs proving (§3). OOPSLA 2025 /
  PACMPL 9(OOPSLA2). <https://dl.acm.org/doi/10.1145/3763167> ·
  <https://github.com/leanprover/leansat>
- **The array/UF sliver (loom-only, phase 3)** is layered *above* bitblasting as
  lazy read-over-write (McCarthy select/store axioms on concrete consecutive
  offsets) + Ackermann expansion for UF congruence — each instantiation adds
  clauses to the same CNF, so it doesn't change the SAT/certificate story. synth
  needs none of this (register-level QF_BV only), so it can burn in phases 1-2
  before the sliver exists (per the #246 synth comment).

**Round-2 conclusion.** Bitblasting is pure-Rust, untrusted, and wasip2-clean.
No native dependency here. The only build is our own AIG/Tseitin code; `bv_decide`
is the reference for *what* to encode and (later, if we go native-Lean) *whose
checker* to reuse.

## 3. Round 3 — the verified-checker decision (the crux)

This is the one **trusted** component. Four routes, judged on (i) does it fit an
existing org Bazel rule set, (ii) can it actually be built/proved, (iii) does the
result run where ordeal runs.

### 3a. Aeneas → Lean (`rules_lean`) — the user's leaning

**Can Aeneas handle an LRAT checker's Rust?** An LRAT checker is:
core-clause store (growable vector of clauses), a per-step **unit-propagation
loop** walking hint clauses, and marking/RAT checks — all over integer/array
data. Against Aeneas's actual envelope:

- **Fits Aeneas's sweet spot in principle:** safe, sequential, no interior
  mutability, no unsafe. Aeneas eliminates memory reasoning via region types and
  produces a pure functional model in Lean.
  <https://arxiv.org/abs/2206.07185> · <https://lean-lang.org/use-cases/aeneas/>
- **Real friction, from the 2026 jxl-rs case study (the honest lens):**
  verification there was **partial** — panic-freedom of *one* function, ~95
  lines of helper lemmas, manual trusted models for missing external functions,
  and invariants that had to be *asked of the author* because they lived in
  English comments. Recent Aeneas handles loops **via combinators** and can show
  termination by a decreasing measure without a full loop invariant *if you only
  want panic-freedom*. But **functional correctness of a UP loop is more than
  panic-freedom** — you must prove the checker only accepts genuinely-derivable
  empty clauses, which *does* need a loop invariant about clause entailment.
  <https://jonathan.protzenko.fr/2026/05/05/jxl-rs.html>
- **Known limits that bite a checker:** `return` inside nested loops and
  `break`/`continue` to outer loops are **"not supported yet"** — a typical UP
  inner loop with early-exit-on-conflict must be written in Aeneas-friendly
  combinator style, not idiomatic imperative Rust. Interior mutability is
  unsupported (fine — a checker doesn't need it). Arrays/vectors are supported
  as functional sequences; overflow/bounds surface as panic-freedom obligations.
  <https://arxiv.org/html/2410.18042v1> (Charon) · Aeneas README.
- **Prior-research lens ("good for prove-once functional models, wrong for
  in-loop solving") applies favorably here.** A *checker* IS a prove-once
  functional model: fixed algorithm, proven once, then trusted forever. That is
  exactly Aeneas's sweet spot — unlike a *solver's* search loop, which is the
  "in-loop solving" Aeneas is wrong for. So the lens **endorses** Aeneas for the
  checker and **warns off** using it for the SAT core (which we don't — the core
  is untrusted). This is the cleanest fit in the whole survey.

**Effort estimate (Aeneas→Lean checker):** medium. Plan ~**2-4 person-months**:
write the LRAT checker in *deliberately Aeneas-shaped* Rust (combinator loops, no
outer-loop break, explicit bounds), get a clean Charon→Aeneas→Lean translation,
then prove **soundness** in Lean: *if the checker accepts, the input CNF is
UNSAT.* The math is not deep (resolution/RUP entailment) but the Lean proof of
the propagation invariant is real work. Risk: an ergonomic mismatch could force
non-idiomatic Rust that's hard to keep in sync with a fast checker.

### 3b. Reuse `bv_decide`'s native-Lean LRAT checker directly

- **Already verified, already merged into Lean core** as `Std.Tactic.BVDecide`
  (leansat archived/absorbed nightly-2024-08-29). Includes a **verified LRAT
  checker AND a verified AIG/bitblaster** over Lean's `BitVec` theory.
  <https://github.com/leanprover/leansat>
- **The catch: it's a Lean tactic/kernel artifact, not a wasip2 library.** To
  "reuse" it you either (a) run Lean as an offline oracle in CI (Lean isn't
  going into a wasip2 component), or (b) re-implement its checker in Rust and
  re-prove — which is exactly route 3a. So "reuse bv_decide directly" really
  means **"use Lean offline to check certificates in CI,"** not "embed it in
  ordeal." That's a legitimate *CI-gate* design (cert emitted by ordeal, checked
  by Lean out-of-band) but it does **not** satisfy "checker runs where ordeal
  runs (wasip2, in-process)." **[wasip2 forces this]**

### 3c. Rocq checker (`rules_rocq_rust`) — coq-lrat / cake_lpr-style

- **coq-lrat exists and is real**, but among verified LRAT checkers it is the
  **slowest** (acl2-lrat fastest, then cake_lpr, then coq-lrat). **cake_lpr**
  (CakeML/HOL4) is verified **down to x64 machine code** and fast, but it's
  HOL4/CakeML, not one of our three Rust-proof rule sets.
  <https://satcompetition.github.io/2025/downloads/checkers/cakelpr.pdf> ·
  <https://www.ncbi.nlm.nih.gov/pmc/articles/PMC7984575/>
- **Org fit:** `rules_rocq_rust` exists and synth already ships a Rocq suite
  (`coq/Synth/`, `//coq:verify_proofs`), and the #246 synth comment explicitly
  offers Rocq-checker co-location as a reuse point. **But** a Rocq-*extracted*
  checker (OCaml) does not run in a wasip2 component either — same
  runs-where-ordeal-runs problem as 3b, plus a proof style with more manual math
  than Aeneas.

### 3d. Verus (`rules_verus`)

- **No existing Verus LRAT checker was found** — this is greenfield. Verus's
  advantage is that it verifies *the actual Rust* in place (no translation gap,
  no combinator rewrite) and the verified Rust then **compiles to wasip2
  directly** — the only route besides 3a where the *proven artifact itself* runs
  in-process. The cost is writing all specs/invariants by hand in Verus and no
  head start.

### Round-3 recommendation

**Primary: 3a — Aeneas → Lean, with 3b (native `bv_decide`/Lean) as a CI
cross-check oracle.** Reasoning:

1. It is the **only** route (besides Verus-greenfield) where the *verified
   artifact runs in-process on wasip2* — you translate/prove once, then compile
   the **same Rust checker** to wasip2 for the in-component path. Routes 3b/3c
   put the verified checker in Lean/Rocq/CakeML runtimes that don't go into the
   component.
2. It **matches the prior-research lens exactly**: a checker is a prove-once
   functional model (Aeneas's strength), not an in-loop solver (Aeneas's
   weakness). We keep the solver untrusted precisely so Aeneas never has to
   touch search.
3. `rules_lean` exists; `bv_decide` gives a **reference implementation to mirror
   and a verified checker to differential-test against** (emit LRAT, check with
   both ordeal's Aeneas-proved checker and Lean's `bv_check` — disagreement is a
   hard error). That de-risks the Aeneas proof.

**Fallback: 3d — Verus** if Aeneas's loop/control-flow limits make the
checker Rust too contorted to maintain. Verus verifies idiomatic Rust in place
and compiles to wasip2, at the price of more hand-written proof and no reuse.

**Explicitly not primary: 3b/3c** as the *in-component* checker — they can't run
in wasip2; keep them as **offline CI oracles** only.

## 4. Round 4 — completeness self-critique (what's still unverified)

Honest gaps and unverified claims:

1. **varisat's 2019 staleness is a standing liability.** No evidence it builds
   clean on current Rust *for wasip2* specifically — that is **unverified** and
   must be the first prototype. If it rots, splr (DRAT + MPL) or a small varisat
   fork are the fallbacks. The proof matrix genuinely lacks an ideal
   pure-Rust + native-LRAT + maintained + Apache/MIT core.
2. **No one has shown an LRAT checker translated by Aeneas end-to-end.** The fit
   is *argued* from Aeneas's envelope + the jxl-rs case study, not demonstrated.
   The nested-loop `break`/`continue` limitation is real and *will* shape how the
   UP loop is written. **Prototype this before committing.**
3. **LRAT-from-varisat overhead is "High" per its own docs** — unquantified at
   ordeal's tiny query sizes. Almost certainly fine (per-op equivalence checks
   are small), but **unmeasured**.
4. **The array/UF sliver's certificate story is hand-waved.** Lazy
   read-over-write and Ackermann add clauses to the same CNF, so the LRAT should
   still cover them — but whether the *lemma instantiation* is itself
   certificate-covered (vs. a trusted preprocessing step) is **not worked out**.
   This is a real soundness question for phase 3; synth is unaffected.
5. **CaDiCaL-on-wasip2 was not found to exist.** Searches surfaced no
   wasip2-native CaDiCaL build; C++→wasip2 via the component toolchain is
   unproven and, combined with wasip2's **no-threads / panic=abort**, is exactly
   the from-source-C++ pain #246 wants gone. Treated as **native-only**.
   <https://blog.rust-lang.org/2024/11/26/wasip2-tier-2/> ·
   <https://doc.rust-lang.org/nightly/rustc/platform-support/wasm32-wasip2.html>

**What to prototype first (in order):**
1. Compile **varisat to `wasm32-wasip2`** and run one hand-written UNSAT CNF,
   capturing LRAT. Kills or confirms the primary core.
2. Write a **minimal LRAT checker in Aeneas-shaped Rust**, run
   **Charon→Aeneas→Lean**, and see what survives. Kills or confirms route 3a
   *before* any proof effort.
3. Bitblast **one op** (`bvadd`, ripple-carry) → AIG → CNF → varisat → LRAT →
   check with Lean's `bv_check` as oracle. End-to-end skeleton of the whole
   trust boundary on a single op.

## 5. Deliverables

### (a) Recommended SAT core — dual path

- **wasip2-primary: `varisat`** (pure Rust, Apache-2.0/MIT, native LRAT). The
  only mature pure-Rust core with a permissive license *and* native LRAT.
  Vendor + pin; be ready to fork for maintenance. **This is the primary, not a
  "fallback"** — correcting `ARCHITECTURE.md`. **[wasip2 forces this]**
- **native fast path: `CaDiCaL`** (C++, MIT, native `--lrat`, CAV'24 2.0) for
  local dev / native CI where raw speed helps. Same LRAT format → **same checker
  validates both**, so the choice is purely performance, never soundness.
- **maintained fallback core: `splr`** if varisat rots — accepting DRAT (needs
  drat-trim→LRAT) and MPL-2.0. Not preferred, but alive and wasm-aware.

### (b) Bitblasting approach

Own, **pure-Rust**, untrusted: term-graph → per-op boolean circuit →
**AIG (structural sharing + const-fold)** → **Tseitin CNF** → SAT. `bv_decide`'s
verified AIG is the blueprint. No native dependency; **wasip2-clean.** Array/UF
sliver layered above as lazy read-over-write + Ackermann (loom-only, phase 3).

### (c) Verified-checker decision

**Aeneas → Lean (`rules_lean`)**, with **native-Lean `bv_decide`/`bv_check` as an
offline CI oracle**. It's the only route where the *verified artifact itself*
runs in-process on wasip2, it matches the "prove-once functional model" lens
exactly, and `bv_decide` gives both a reference and a differential oracle.
**Effort: ~2-4 person-months**, dominated by the Lean soundness proof of the
propagation invariant (the math is shallow; the loop-invariant proof is the
work). **Fallback: Verus** (`rules_verus`) — verifies idiomatic Rust in place and
compiles to wasip2, at the cost of all-manual specs and zero reuse. Rocq
(`coq-lrat`) and native-Lean-as-checker are **CI oracles only** — they cannot run
in the component. **[wasip2 forces this away from 3b/3c as the in-component
checker]**

### (d) wasip2-feasibility verdict — honest

**Feasible, and it flips the architecture.** wasip2 has **full std**, but **no
threads** and **panic=abort**. A single-threaded pure-Rust CDCL core (varisat)
fits cleanly; the pure-Rust bitblaster fits cleanly; an Aeneas- or Verus-proved
Rust checker fits cleanly. What does **not** fit wasip2 in-process: **CaDiCaL
(C++ from source)** and **any Lean/Rocq/CakeML checker runtime**. So the
`ARCHITECTURE.md` "CaDiCaL primary / varisat fallback" framing is backwards *for
the target that motivates the project*: **pure-Rust is primary on wasip2**;
CaDiCaL is the native accelerator. The C++ static-link pain #246 wants gone is
*reintroduced* the moment CaDiCaL is the primary path, so it must not be.

### (e) Phased plan (aligned to ordeal's existing P0-P3)

- **P0 (done):** skeleton, closed fragment, `Unknown`-sound stub.
- **P1 — bitblast + SAT:** pure-Rust AIG/Tseitin; **varisat wasip2-primary +
  CaDiCaL native**; SAT→Model; Z3 differential oracle. *Prototype #1 + #3 above
  gate entry.* synth is the cleanest phase-1 corpus (register-level QF_BV, no
  sliver).
- **P2 — certificate-checked:** LRAT emission (varisat native / CaDiCaL native);
  **Aeneas→Lean checker** proved sound; Lean `bv_check` as differential oracle;
  model self-check for SAT. *Prototype #2 gates the Aeneas commitment.*
- **P3 — sliver + integration:** lazy read-over-write + Ackermann (loom-only);
  corpus burn-in vs Z3; drop `static-link-z3` from the critical path.

### (f) Open questions / prototype-first

1. Does **varisat build & run on `wasm32-wasip2`** today? (Prototype #1 — highest
   risk, cheapest to answer.)
2. Does an **LRAT checker survive Charon→Aeneas→Lean** without contorting the UP
   loop past maintainability? (Prototype #2 — gates route 3a vs Verus fallback.)
3. Is the **array/UF sliver certificate-covered**, or does lemma instantiation
   become a trusted preprocessing step? (Phase-3 soundness question.)
4. LRAT-generation **overhead at ordeal's query sizes** — measured, not assumed.
5. Is a small **varisat maintenance fork** warranted given 2019 staleness, or is
   **splr + DRAT→LRAT + MPL acceptance** the lower-effort path?
